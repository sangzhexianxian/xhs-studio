# 为什么做这个

## 一、生成不难，落地才难

2025 年这类"文字转图文"的工具已经很多。它们的共同终点是 `output/` 目录：
九张 PNG，整齐排列，然后你打开手机相册——

发现什么也没有。

接下来是：长按第一张 → 保存 → 再长按第二张 → 保存 → ……
九次之后，图片顺序错了两张，其中一张存成了 HEIC，发到 App 里被压糊。

这段摩擦没人愿意做，但它决定了这东西**到底有没有被用起来**。

所以这个仓库的重心不在"生成"，在**从生成到发布之间那 10 厘米**。
我们为此写了一个安卓壳：点一次，九张整批进 `Pictures/我的图文/`，
顺序正确、文件名正确、不用授权相册权限。

## 二、纯网页为什么做不到

浏览器（无论 Chrome 还是 Safari）都没有"静默写系统相册"的 API，这是安全模型的一部分，
不是实现难度问题。能用的替代品只有三个：

1. `<a download>`：逐张落到"下载"目录，不进相册；
2. `navigator.share({files})`：拉起系统分享，用户在弹层里自己选"保存图片"——最接近，但仍需一次人工确认；
3. File System Access API：桌面 Chrome 可写目录，手机端基本不可用。

所以我们**三条都做了**，按设备能力自动降级；同时提供一个 17 KB 的壳，
把这最后一个确认也省掉。不假装纯网页能做到，也不因此放弃网页版。

## 三、为什么固定九页

不是"九宫格好看"，是九个功能位置各有其职：

- 第 1 页决定点击率（结果前置）
- 第 2 页决定是否继续划（只留人和具体处境）
- 第 3–5 页决定是否被信服（判断 → 依据 → 取舍）
- 第 6 页决定"这人真的在做"（作品墙）
- 第 7–9 页决定是否被记住、是否关注

大多数 AI 图文的问题是第一页就在解释背景，第七页还在解释背景。

## 四、为什么要有事实墙

这类工具最危险的地方不是画得丑，是**替你编经历**。

模型很擅长写出"我坚持了 21 天，破过三次"这类句子——它知道这样像人写的。
但如果你没做过，这句话就是在替你撒谎，而且是以第一人称。

`guard.py` 的做法很笨但有效：把改写稿里所有"数字 + 量词"抽出来，
跟你的原稿比对，凡是原稿没有的（三个月、两周、十几版、两遍），
一律判硬伤，带着清单让模型重写一轮。

它救过我很多次。这比任何华丽的版式都重要。

## 五、它不做什么

- 不调平台接口自动发布（小红书没有开放发布接口，任何"一键发布"都是模拟登录，风险极高）
- 不做多账号、不做矩阵、不做"一天出 50 篇"
- 不保证内容好——**内容是你的事**，它只保证形式不拖后腿

如果这三条里有你需要的，这个仓库不适合你。
